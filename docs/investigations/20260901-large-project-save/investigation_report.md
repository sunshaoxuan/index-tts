# 大型工程分句重生成请求体超限调查

## 用户现象

在白夜行02点击分句重新生成时，页面提示 `Request body is too large`。

## 根因

失败请求是分句任务提交前的工程 PUT。工程磁盘文件约 37 MiB，209 条导演历史中有 208 条携带完整工程快照，压缩后的历史字段约 25.79 MiB，超过 Fastify 全局 25 MiB 请求体限制。分句重生成 POST 当时没有执行。

## 修复

1. 浏览器保存工程时省略服务端管理的 `director_history` 和 `director_memory`。
2. 工程 GET 和 PUT 响应保留历史摘要，省略完整 snapshot。
3. 磁盘持久化继续保存完整审计快照和最新导演记忆。
4. 工程 PUT 单路由提供 64 MiB 兼容上限，使部署前已经打开的旧页面能够完成一次大型保存并收到轻量响应。

## 真实运行验收

部署后，来自 `ivs.briconbric.com` 的白夜行02保存请求返回 200，耗时约 1.137 秒；随后的分句 59 重生成请求返回 202。任务完成并生成三版候选，其他分句没有进入推理。新主片断和三版候选在浏览器中均达到 `readyState 4`，时长约 1.75 至 1.83 秒。

工程 API 响应约 0.468 MiB，返回 214 条历史摘要且 snapshot 数量为 0。磁盘文件约 38.03 MiB，保留 213 条历史 snapshot 和完整 `director_memory`。部署后容器日志没有新的请求体超限错误。
