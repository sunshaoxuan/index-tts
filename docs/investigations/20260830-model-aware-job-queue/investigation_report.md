# 模型感知后台任务调度调查报告

## 问题

当多个后台生成任务竞争模型资源时，系统需要按模型与依赖排队。可运行且没有依赖阻塞的任务应优先复用驻留模型，再考虑切换模型。

## 已确认现状

改动前，Node 服务只保存一个 `activeJob`。任何第二个后台任务都会收到 HTTP 409。VoiceDesign 与 IndexTTS 已有双向释放协议，服务端缺少可以利用该协议减少模型切换的上层队列。

## 实现结论

1. 后台任务使用稳定模型键。全文分析键包含 Provider、Endpoint 与模型名，音色和音频任务使用各自稳定引擎键。
2. 同一工程的后续任务依赖此前所有活动或等待任务。不同工程之间不自动建立依赖。
3. 调度先筛选依赖全部完成的任务。在可运行集合中先选择上一驻留模型对应任务，再按进入时间和任务 ID 排序。
4. 依赖失败会使后续任务进入明确错误终态。
5. 等待队列和上一模型键通过临时文件与原子重命名写入 `runtime-output/product-jobs/job-queue.json`。服务启动时恢复未终止等待项。
6. 活动任务和等待任务都锁定工程写入、删除与生成资产修改入口。
7. 依赖任务状态文件缺失时，后续任务进入明确错误终态，避免永久等待。

## 覆盖边界

本次覆盖后台 AI 全文分析、角色音色、完整音频、严格串接和分句重新生成。人物小传扩写和角色画像是同步 HTTP 调用，未纳入本次后台队列。

## 风险

真实 GPU 模型切换耗时与长任务吞吐量仍需要在部署镜像中观察。调度算法和持久状态已经由隔离服务测试覆盖，真实模型队列压力证据待运行环境验收补充。
