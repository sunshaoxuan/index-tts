# Ollama 自主管理模型与后台任务队列调查

## 问题

全文 AI 分析任务 `1f9894b7d3cd4571816227be6bdea5bd` 在逐块处理中反复释放显存并重新装入同一模型。产品目标是前端提交后立即入队，调度器按依赖和模型亲和性消费任务，模型生命周期由 Ollama 管理。

## 运行证据

任务于 2026-09-09 00:53:26 JST 开始，01:05:28 JST 完成，总耗时约 12 分钟。Product Studio 和 Ollama 容器均未重启，也未发生 OOM。

Ollama 在任务期间为同一模型交替启动 `-c 8192` 与 `-c 16384` runner。旧 Python Worker 的空请求预热和全部结构化请求都显式发送 `num_ctx=8192` 与 `keep_alive=30m`；Ollama 容器默认配置为 `OLLAMA_CONTEXT_LENGTH=16384`、`OLLAMA_KEEP_ALIVE=-1`、`OLLAMA_MAX_LOADED_MODELS=1` 和 `OLLAMA_NUM_PARALLEL=1`。

15:57:39、15:59:39、16:01:39 和 16:03:39 UTC 的 `/api/chat` 在 120 秒返回 499。Ollama 同时记录客户端在 llama-server 装入完成前断开、装入被取消和 `context canceled`。每次同一约 11.20 GiB 模型 runner 重建耗时约 60 至 86 秒。

Ollama 历史访问日志不记录请求体或可区分的客户端身份。可以确认 `8192` 请求来自旧 Worker，也可以确认 `16384` 与服务默认上下文一致；现有证据无法把每次 `16384` 请求归属到具体进程。这个归属缺口不影响修复，因为所有 Product Studio Ollama 请求不再覆盖服务端上下文。

## 根因

应用层同时控制模型预热、保活和请求级上下文，破坏了 Ollama 的统一 runner 管理。请求级 `8192` 与服务默认 `16384` 形成 runner 参数竞争；后台 Worker 的 120 秒热请求超时又会在合法装入尚未完成时主动断开，导致已付出的装入成本作废并再次重建。

## 修复

1. 删除全文分析 Worker 的空请求预热和 `loading_model` 阶段。
2. Ollama 结构化请求不再发送 `keep_alive` 或 `num_ctx`，只保留模型、消息、结构化输出格式和确定性采样参数。
3. 后台请求统一使用 600 秒等待窗口，允许 Ollama 自然装入和完成推理。
4. 保留持久队列、依赖门、同模型任务优先和稳定排序。模型键仅用于选择下一个任务，不触发加载、卸载或保活。
5. 提交接口继续立即返回 HTTP 202 和任务 ID，React 通过 `/api/jobs/:id` 轮询状态并在终态取回结果。

## 验收边界

代码和单元测试只能证明请求契约与队列行为。生产验收还必须核对镜像 revision、容器健康、浏览器提交与轮询、Console、截图，以及真实连续推理期间 runner 上下文不再交替。
