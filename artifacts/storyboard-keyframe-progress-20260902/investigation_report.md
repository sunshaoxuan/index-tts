# 镜头级画面小记、关键帧进度与锁定调查报告

## 严重问题结论

白夜行01 第一场景的旧分镜在镜头切分阶段把同一个场景小记拼到每个镜头，导致不同音频时间范围虽然具有不同原文，`storyboard_note` 仍以同一句场景描述开头。图像服务继续把这个字段作为提示主体，最终形成高度重复的生图提示。

修复后采用两阶段流程。第一阶段只建立稳定镜头 ID、起止分句、可选音频时间和完整 `source_text`。第二阶段由文本导演逐镜头读取自身原文，返回独立标题、画面小记、原文连续取景证据和实际可见人物 ID。校验器要求 ID 完整覆盖、证据属于当前镜头原文、描述具有足够视觉信息且不能完全重复、人物属于登记角色并排除旁白。任何批次三次校验仍失败时，本次全量分镜终止且旧工程保持原状。

人物连续性在 AI 输出之外增加确定性补充。系统识别当前镜头原文明示姓名，并在同一场景最近只有一个明确人物时把后续“他、她、自己”等代词解析到该角色。确定性人物 ID 强制并入 `participants`，关键帧生成继续按稳定角色 ID 使用角色资产原图。

白夜行01 第一场景 8 个镜头在不写回生产工程的内存副本中使用本机 `qwen3:14b` 实跑。8 个稳定 ID 全覆盖，8 条取景证据均属于各自原文，8 条画面小记全部唯一，角色 `role_001` 出现在镜头 2、3、4、6、7。模型首轮质量不合格后整批重写，总计 2 次请求、6371 prompt tokens、2067 output tokens、177.218 秒。生产 `project.json` 保持原状，使用者需要执行“AI 重新生成全部分镜”更新旧镜头。

## 问题结论

原全量关键帧入口把全部镜头作为一次 HTTP 请求提交。服务端完成全部图片后才统一返回，前端只有按钮加载状态。73 张图片生成期间，页面无法给出已完成数量、当前镜头和剩余时间，分镜字段仍可编辑，工程输入存在漂移风险。

## 行为链路

1. 前端从 `document.scenes[].shots[]` 建立稳定镜头队列。
2. 全量生成先调用 `POST /api/projects/:id/storyboard/keyframes`，请求体包含 `preflightOnly: true`。
3. 服务端检查全部镜头小记、稳定角色 ID、当前工程与关联工程角色参考图，不发出图像请求。
4. 预检通过后，前端按队列逐张调用单镜头关键帧接口。
5. 每张成功后立即把图片、提示、风格、模型、生成时间和身份参考记录回写到当前工程状态。
6. 状态机持续发布预检、生成中、完成、取消和失败状态，并计算完成数量、百分比、当前镜头、已用时间和预计剩余时间。
7. 生成期间 `projectLocked` 统一锁定分镜字段、镜头选择、合并、拆分、手工创建、工程切换、保存、AI 设置和冲突生成入口。
8. 完成、取消或失败后解除锁定。已成功生成的图片继续保留，失败状态定位到具体镜头。

## 运行时结果

隔离 Product Studio 使用真实 73 镜头工程的副本，保留工程结构和角色资产，把浏览器验收范围缩减为 3 个连续镜头。图像服务由本机延迟 mock 提供，每张等待 2.2 秒，不调用外部付费服务。

桌面页面实际观察到 `0 / 3`、`1 / 3`、`2 / 3`、`3 / 3`。`1 / 3` 时工程切换、保存、镜头小记、全量风格和拆分按钮均为 disabled，当前镜头为第 2 张，预计剩余约 5 秒。模拟第 2 张失败后页面保持 `1 / 3`，第 1 张图片仍在 DOM 中，保存与工程切换恢复可用。单张生成显示“等待图像服务响应”，并提供取消这一张。

最终复验使用 3 个连续镜头，其对应原文、AI 取景证据和画面小记均不同。镜头 2 与镜头 3 显示“最近生成已使用 1 张角色参考图”，角色均为笹垣润三。桌面实际观察到 `0 / 3`、`1 / 3`、`3 / 3`；`1 / 3` 时保存、AI 全量分镜、手工创建和三个拆分按钮均为 disabled，完成后全部解除锁定。

390 像素移动端发现过场景标题和右侧标签重叠，返工后场景卡头部改为两行网格布局。最终矩形检查得到标题底部 `1504.4375`、标签顶部 `1514.4375`，`overlap=false`；`clientWidth=375`、`scrollWidth=375`、`bodyScrollWidth=375`，无横向溢出。浏览器 Console error 0、warning 0。
